Practical Demonstration

1. Successful event

Publish a normal event and verify the successful processing message in the Spring Boot terminal.

2. Duplicate event

Submit the same event ID again and verify the duplicate-skipped message in the consumer logs.

3. Retry and exponential backoff

Enable simulated failure and observe retry messages and increasing wait times in the backend logs.

4. Dead-letter queue

After retries are exhausted, use the Kafka console consumer to confirm the event was published to the DLQ.

5. Idempotency limitation

The current processed-event set is in memory, so it resets when the application restarts. Durable idempotency would require persistent storage.

Kafka Read/Write Policy

This page documents the application's configured data flow. It is an application-level policy summary, not Kafka ACL enforcement.

WRITE

Producer → scheduled-posts

The Spring Boot REST API accepts a post event and the producer publishes it to the main Kafka topic.

  • Endpoint: POST /api/posts
  • Topic: scheduled-posts
  • Producer acknowledgements are configured as all.
READ

Consumer ← scheduled-posts

The ScheduledPostConsumer listens to the main topic using consumer group scheduled-posts-group.

  • Reads events from scheduled-posts.
  • Checks event IDs before processing.
  • Failures go through the configured retry handler.
WRITE AFTER FAILURE

Recoverer → scheduled-posts-dlq

When processing still fails after retries, the configured dead-letter recoverer publishes the failed record to the DLQ.

  • Destination: scheduled-posts-dlq
  • Configured to preserve the source partition number.
  • Failure headers contain exception and source-record details.
READ FOR INSPECTION

DLQ viewer → scheduled-posts-dlq

GET /api/dlq reads DLQ records for display using a separate temporary consumer identity.

  • Reads from the beginning for inspection.
  • Shows event ID, content, partition, offset, timestamp and failure headers.
  • Refreshing reads the topic again; it does not delete messages.

Ordering and Duplicate Prevention

Ordering policy

Kafka guarantees order within a single partition. With three partitions, records in different partitions do not have one guaranteed global order. The configured DLQ mapping sends a failed record to the matching partition number.

Explain to the teacher: Partition and offset identify a record's position within that partition. Offsets from different partitions are not one global sequence.

Idempotency policy

The consumer checks eventId. If the ID is already in the processed-ID set, the event is skipped. Otherwise, it processes the event and records the ID after success.

Limitation: the current set is in memory and resets when Spring Boot restarts. Persistent storage is required for durable deduplication across restarts.

Security note: this is a documented read/write flow, not a Kafka ACL security boundary. The current local PLAINTEXT setup does not demonstrate authenticated topic-level permissions. ACLs can be added separately for production-style access control.
